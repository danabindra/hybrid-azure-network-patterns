    NIST SP 800-207 Zero Trust control mapping¶

    Purpose¶

    This document maps NIST SP 800-207 (Zero Trust Architecture) tenets and logical components to the specific controls implemented in the NewCo hybrid Azure network architecture. It serves as a compliance reference for security reviews, audit preparation, and architecture decision records.

    Zero Trust tenets (Section 2.1)¶

    # NIST 800-207 tenet Implementation in this architecture
    1 All data sources and computing services are considered resources Every spoke workload, hub NVA, shared service, and SaaS integration is treated as a discrete resource with its own NSG, UDR, and identity controls
    2 All communication is secured regardless of network location ExpressRoute provides private L2 paths; NVA enforces L3-L7 inspection on all flows including intra-Azure; Front Door uses TLS 1.2+ end-to-end
    3 Access to individual enterprise resources is granted on a per-session basis NVA policy evaluates each flow independently; no implicit trust from prior sessions; NSG stateful rules track per-connection state
    4 Access is determined by dynamic policy NVA VMSS applies centrally managed rulesets (FortiManager/SmartConsole) that update without redeployment; WAF rules on Front Door support real-time tuning
    5 Enterprise monitors and measures integrity and security posture of all assets Log Analytics workspace aggregates NVA syslog, NSG flow logs v2, Front Door access/WAF logs, and NAT Gateway metrics; Sentinel provides cross-signal correlation
    6 All resource authentication and authorization are dynamic and strictly enforced Azure AD (Entra ID) authentication for management plane; NVA applies identity-aware policy where integrated with directory services
    7 Enterprise collects information about the current state of assets and uses it to improve security posture NetBox tracks device inventory and IPAM; NVA health probes and VMSS autoscaling respond to real-time state; Front Door health probes drive origin selection

    Logical component mapping (Section 3.1)¶

    NIST 800-207 component Role Azure implementation
    Policy Engine (PE) Decides whether to grant access NVA security policy (FortiGate/CheckPoint ruleset); Front Door WAF managed rules; NSG rules
    Policy Administrator (PA) Establishes and manages access policy FortiManager or CheckPoint SmartConsole (centralized NVA management); Azure Policy for resource compliance; Front Door WAF policy
    Policy Enforcement Point (PEP) Enables, monitors, and terminates connections Hub NVA VMSS (inline inspection); Front Door WAF (inbound web); NSGs (subnet-level filtering); UDRs (traffic steering)
    Policy Information Point (PIP) Provides data for policy decisions Log Analytics / Sentinel (security telemetry); NetBox (asset inventory); Azure AD (identity); NVA threat intelligence feeds
    Subject Entity requesting access Spoke workloads, branch users, external web clients, OCI cross-cloud services
    Enterprise resource Target system Spoke-hosted applications, databases, storage accounts, shared services in hub

    Pattern compliance summary¶

    Branch to Azure (ExpressRoute / SD-WAN)¶

    Control area Implementation
    Network segmentation Hub-spoke topology with no direct spoke-to-spoke peering; branch traffic enters only through hub
    Inspection All branch-to-spoke flows traverse hub NVA for L3-L7 inspection
    Encryption ExpressRoute private peering (L2 isolation); optional IPSec overlay for additional assurance
    Monitoring NVA logs, ExpressRoute circuit metrics, and NSG flow logs to Log Analytics
    Least privilege Spoke UDRs restrict reachable destinations; NSGs deny by default

    Internet egress via hub NVA¶

    Control area Implementation
    Network segmentation Single auditable egress point through hub; no per-spoke internet breakout
    Inspection NVA applies URL filtering, IPS, and TLS inspection on all outbound flows
    Access control NVA policy enforces per-workload egress rules (FQDN allowlists)
    Monitoring NVA syslog, NAT Gateway SNAT metrics, NSG flow logs; alert on port exhaustion
    DDoS protection Azure DDoS Protection Standard on hub VNet public IPs

    Internet ingress via Front Door¶

    Control area Implementation
    Network segmentation Origins have no public IP; Private Link provides backbone-only connectivity
    Inspection Front Door WAF (OWASP CRS, bot protection, rate limiting) as PEP for all inbound web traffic
    Origin cloaking Private Link ensures origins are unreachable from the public internet even if WAF is misconfigured
    Monitoring Front Door access logs, WAF logs, and health probe logs to Log Analytics
    TLS Azure-managed certificates or Key Vault integration; TLS 1.2+ enforced

    Region-to-region transit¶

    Control area Implementation
    Network segmentation Frontend/backend spoke separation per region; no direct spoke peering
    Inspection Dual NVA inspection (both source and destination region hubs) for every cross-region flow
    Encryption Global VNet peering uses MACsec on Microsoft backbone; optional NVA-to-NVA IPSec
    Policy consistency Centralized NVA management plane pushes identical policy to both regions
    Monitoring Cross-region flow correlation in single Log Analytics workspace

    Multi-cloud connectivity (Equinix ECX Fabric)¶

    Control area Implementation
    Network segmentation Cross-cloud traffic enters Azure through hub ExpressRoute gateway and traverses NVA
    Inspection Hub NVA inspects all Azure-to-OCI and OCI-to-Azure flows
    Route security BGP prefix filters and maximum-prefix limits prevent route leaks between clouds
    Encryption Private circuit (L2 isolation); IPSec overlay available for sensitive workloads
    Monitoring NVA logs correlated with OCI VCN flow logs in unified SIEM

    Hybrid DNS resolution¶

    Control area Implementation
    Centralized resolution All DNS queries route through hub Private DNS Resolver; no direct external DNS from spokes
    Conditional forwarding Forwarding rulesets control which domains resolve on-premises vs Azure
    Exfiltration prevention DNS query logging enables detection of tunneling and anomalous patterns
    Access control RBAC restricts private DNS zone modifications; VNet links limit resolution scope

    NetBox IRM integration¶

    Control area Implementation
    Asset inventory Complete IP plan, circuit tracking, and device inventory in NetBox
    Network isolation NetBox runs in hub shared-services subnet with no public IP; NSG-restricted access
    API security Scoped API tokens stored in Key Vault; 90-day rotation policy
    Audit trail NetBox change logging forwarded to Log Analytics

    Audit evidence sources¶

    Evidence type Source Retention
    Network flow logs NSG flow logs v2 (all subnets) 90 days in Log Analytics, 1 year in Storage
    Firewall logs NVA syslog (FortiGate/CheckPoint) 90 days in Log Analytics, 1 year in Storage
    Web application logs Front Door access and WAF logs 90 days in Log Analytics
    DNS query logs Private DNS Resolver diagnostic logs 90 days in Log Analytics
    Configuration changes NetBox change log, Azure Activity Log 90 days (Activity Log), indefinite (NetBox)
    Route table state Azure Resource Graph queries Point-in-time snapshots via scheduled queries
